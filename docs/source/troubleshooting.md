# Troubleshooting

## Build failures

### PetaLinux build fails with `bitbake petalinux-image-minimal failed` and sstate fetch errors

If a `./build.sh petalinux --target <board>` run ends with errors like

```
ERROR: <package>-<ver>-r0 do_..._setscene: Fetcher failure: Unable to find file file://.../sstate:...
[ERROR] Command bitbake petalinux-image-minimal failed
```

the actual build is not broken. These `_setscene` errors come from
bitbake trying to pull prebuilt artifacts from the public Xilinx
sstate-cache mirror, which occasionally returns 404 for individual
packages. Bitbake falls back to building those packages locally and
succeeds, but still exits non-zero because of the failed fetches —
so the build runner stops before the `petalinux-package` step that
produces `BOOT.BIN`.

**Fix: just re-run the same command.** The second attempt finds the
missing packages in the local sstate cache (populated by the first
run) and completes cleanly, producing `BOOT.BIN`. The reference
design itself is fine; this is a transient issue with the public
mirror.

### Bitstream generation fails with `[Common 17-69]`

If the `xsa` stage fails at `write_bitstream` (Zynq UltraScale+) or `write_device_image`
(Versal) with

```none
ERROR: [Common 17-69] Command failed: This design contains one or more cells for which bitstream generation is not permitted:
sfp_i/xxv_ethernet_0/inst/..._CORE (<encrypted cellview>)
```

then Vivado did not find a license for the XXV Ethernet IP that permits bitstream generation.
Earlier in the log you will find
`WARNING: [IP_Flow 19-650] IP license key 'xxv_eth_mac_pcs@2025.05' is enabled with a Design_Linking license.`
Install a full or hardware-evaluation license for the 10G/25G Ethernet Subsystem (see
[Licenses](requirements.md#licenses)). An evaluation license is time-limited: a build that
starts after it has expired fails in the same way.

After installing the license, clean the target and build it again — Vivado keeps the IP output
products that were generated without the license and does not pick up the new license until
they are regenerated:

```
./build.sh clean --stage xsa --target <target>    # deletes the Vivado project of the target
./build.sh xsa --target <target>
```

### `CRITICAL WARNING: [Vivado 12-1790] Evaluation License Warning`

This critical warning appears in every build of this design, because the XXV Ethernet IP has
separately licensed features. It does not stop the build and can be ignored. If you are using an
evaluation license, see [Licenses](requirements.md#licenses).

### General build issues

Check the following if the project fails to build or generate a bitstream:

1. **Are you using the correct version of Vivado for this version of the repository?**   
   Check the version specified in the Requirements section of the README.md file. Note that this project is regularly updated
   and you may have to refer to an earlier commit of this repo if you are using an older version of Vivado.

2. **Did you correctly follow the build instructions?**   
   Please check the build instructions carefully as you may have missed a step.

3. **Did you copy/clone the repo into a short directory structure?**   
   Windows doesn't cope well with long directory structures, so copy/clone the repo into a short directory structure such as
   `C:\projects\`. When working in long directory structures, you can get errors relating to missing files, particularly files 
   that are normally generated by Vivado (FIFOs, etc).

## Boot issues

### No output on the UART at power-on

* Check that the boot-mode switches are set to SD boot (see
  [Boot PetaLinux](petalinux.md#boot-petalinux)).
* **Yocto images:** check that `BOOT.BIN` was copied onto the first (FAT) partition of the SD
  card after writing the wic image. The wic image itself does not place `BOOT.BIN` where the boot
  ROM can read it (see [Prepare the SD card](yocto.md#prepare-the-sd-card)).

### Versal (Yocto): U-Boot stops at its prompt instead of booting Linux

U-Boot loads Linux through systemd-boot from `EFI/BOOT/BOOTAA64.EFI` on the first partition of
the SD card. The wic image ships that folder empty. Copy `BOOTAA64.EFI` from the boot-image zip
(or extract it from `rootfs.tar.gz`) to the card as described in
[Prepare the SD card](yocto.md#prepare-the-sd-card).

## SFP28 port issues

The kernel messages of the SFP28 ports are the quickest way to find a problem:

```
dmesg | grep -E 'sfp sfp-eth[0-9]'
dmesg | grep -iE 'xilinx_axienet|GT reset|DMA reset|Link is'
```

### `XXV MAC GT reset not complete` and `DMA reset timeout`

```none
xilinx_axienet 80060000.ethernet: __axienet_device_reset: DMA reset timeout!
xilinx_axienet 80060000.ethernet end0: XXV MAC GT reset not complete! Cross-check the MAC ref clock configuration
xilinx_axienet 80060000.ethernet: axienet_device_reset failed
```

on every SFP28 port means that the transceivers have no reference clock, or that it was not
stable when the ports were reset. The ports stay down. Check:

1. **The Quad SFP28 FMC is on the connector the image was built for.** Each target is built for
   one FMC connector — for example `zcu106_hpc0` for HPC0 and `zcu106_hpc1` for HPC1. An image
   for one connector does not work with the card on the other.
2. **VADJ is enabled.** The Si5328 and the I2C bus of the card are powered from the FMC VADJ
   supply. The images enable VADJ at boot: the FSBL on the ZCU104 (patched to read the FMC
   EEPROM) and U-Boot on the VCK190, VMK180, VPK120 and VPK180; on the other boards VADJ is set
   by the board's standard boot flow. If you replace the FSBL or U-Boot, keep these changes.
   With VADJ off, the Si5328 is not found on the I2C bus at boot (no `si5328 probe successful`
   line).
3. **Zynq UltraScale+ with your own kernel:** the kernel must include the patch
   `0001-xxv-qpllreset-gpio.patch` from the BSP, and the device tree the `qpllreset-gpios`
   property (from `port-config.dtsi`). Without them the shared QPLL does not lock again after
   Linux programs the Si5328, and all ports fail as above. Earlier Yocto builds of this design had
   this problem; the Yocto BSPs of this release include the patch.

### `XXV MAC block lock not complete!` at boot

```none
xilinx_axienet 80000000.ethernet end0: XXV MAC block lock not complete! Cross-check the MAC ref clock configuration
```

When a port is opened before its link partner is connected or before the link has trained, the
driver reports that the receiver has no block lock yet. If the port reports `Link is Up` once
the partner is connected, this message can be ignored.

### `unsupported SFP module: no common interface modes`

```none
sfp sfp-eth1: module OEM              SFP-25G-SR-S-MST rev 1.0  ...
xilinx_axienet 80010000.ethernet eth1: unsupported SFP module: no common interface modes
```

The module does not support the line rate of the target, for example a 25G-only SFP28 optic in
a 10G target. The port never gets a carrier. Use a module that supports the target's rate (see
[SFP modules and link partner](requirements.md#sfp-modules-and-link-partner)).

### Messages that are expected

* `sfp sfp-eth0: No tx_disable pin: SFP modules will always be emitting.` — the design ties
  `TX_DISABLE` low, so the transmitters are always enabled.
* `xilinx_axienet 80030000.ethernet: Ethernet core IRQ not defined` — the interrupt output of the
  XXV core is not connected; the driver works from the AXI DMA interrupts.

### The port has a module but no link

* Check the cage LEDs: red means the module receives no signal (`RX_LOS`) — check the cable or
  fiber and the link partner's port.
* Check that the link partner runs at the target's rate with auto-negotiation and FEC turned off
  (see [Link partner settings](testing.md#link-partner-settings)). 25G partners often enable FEC
  by default.
* Check that both ends use modules of the same type (for example both SR optics, or both
  10GBASE-T copper modules).

### Ports not working

Check the following if you are unable to get ports working.

1. **Check the interface-to-port assignment for your design**   
   The assignment of network interfaces (eg. `end0`, `end1`, `eth2`, etc) to physical Quad SFP28 FMC ports (port 0, 1, 2 and 3) is specific to the design and
   to the Linux flow that you are using. It is documented in [PetaLinux port configurations](petalinux.md#port-configurations)
   and [Yocto network interface names](yocto.md#network-interface-names).

2. **Each port must be assigned to a different subnet**   
   If you assign one interface to IP address 192.168.1.10, then you must use a different subnet for the IP address of the other interfaces.
   Multiple ports that are managed under Linux must be assigned to different subnets, or they will not work.
   An example address assignment would be `end1`=192.168.1.10, `eth2`=192.168.2.10, `eth3`=192.168.3.10, `eth4`=192.168.4.10 on a four-port AMD ZCU* design.

## Board Ethernet port (RJ45) issues

### Yocto: link up at 1G but no packets pass

Earlier Yocto builds of this design did not describe the TI DP83867 PHY of the board's own
Ethernet port, so Linux used the generic PHY driver without the RGMII delay settings: the link
came up at 1 Gbps but no packets were received. The Yocto BSPs of this release describe the PHY
in `system-user.dtsi`. If you see this with your own device tree, check that the `ethernet-phy`
node of the GEM carries the `ti,rx-internal-delay` / `ti,tx-internal-delay` properties.
